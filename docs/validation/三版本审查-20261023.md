# AI Loop 三版本审查与实施方案

日期：2026-10-23。源码基准：`22075ec`，core/Codex/DSH 版本号均为 4.5.2。读取了《设计说明.txt》《临时笔记.txt》、源包规则、当前交接、共享协议、安装适配、原生角色生成、DSH 派发与工作区面板、Codex 配置与入口，并执行了隔离测试及针对性复现。本轮是现状诊断，没有修改产品源码、个人配置或安装副本，也没有正式独立评审结论。

## 结论

三端已有相当完整的任务状态、快照、批次、防重复与恢复设计，但不能认定已满足“真实调用子代理、可追溯、适配各 harness、三个版本完整可用”的验收要求。DSH 有真实原生派发代码；Codex 正确生成原生角色，但是否调用仍由当前会话执行；core 是协议与工具包，当前独立发行包不包含原生安装适配。最关键的共同缺口是：独立评审通过尚未与原生调用证据绑定。

## 发现（按影响排列）

### 1. P1，三端共享：独立评审可在零子代理记录时通过【已复现】

位置：`core/scripts/loop.mjs:248`、`:253`、`:350`、`:425`。

`checkReview` 只检查报告的 `execution === independent`，没有关联 activity/agents 台账、原生执行 ID、父子上下文与执行批次。隔离复现创建 managed_execution + independent 任务，在有匹配快照及 tester 日志的情况下，由同一脚本提交声明为 independent 的 reviewer 报告，任务进入 `done`，原生记录数为 0。

这不是证明模型会故意造假，而是证明现有程序门禁不能发现遗漏调用或误标独立上下文。文档禁止冒充，程序却无法帮助识别。Codex、DSH 均使用此核心，都会继承缺口。

建议：新执行契约为报告关联 execution_id、harness、native_id、run/task/role/attempt、上下文隔离类型和证据来源；验收核对角色、批次、终态与 revision，并在最终整体评审同样检查。未知身份、没有执行记录、同一主上下文只能保留未验证/self。记录仍应标明是宿主观察还是调度者填报，不能把人工字符串变成身份认证。

### 2. P1，DSH：强制委派系统提示与叶角色及关闭策略冲突【提示生成已复现；真实模型行为待验收】

位置：`dsh/index.mjs:34`、`:40`、`:128`；对照 `core/WORKFLOW.md` 和 DSH 技能。

4.5.2 对工程任务无条件要求委派并禁止主代理直接编码，没有区分 lite、角色关闭、用户要求单代理和叶子子代理。给 depth=1 的子代理调用上下文生成器，仍返回“必须通过 ai_loop_delegate 派发”的提示，而委派工具又拒绝 depth>0。可能造成叶角色拒绝执行、反复调用后被拒或主代理在角色全关时无路可走。

建议：主代理提示按工作流模式与有效角色生成；叶角色使用执行本角色、不得再派发的专用提示。为确实要求多代理的运行提供明确策略：能力不足/角色未启用时阻塞并说明，不能静默转为单代理，也不能未经选择替用户开启模型。

### 3. P1，DSH：保存使用未确认完整的工作区列表清除其他配置【组件夹具已复现】

位置：`dsh/client/index.mjs:945`、`:1002`。

保存只要 effectiveWorkspaces 非空就过滤 projects，未核对原生列表 phase/state。向面板提供 phase=loading 的部分列表，再保存，会删除尚未出现在列表中的工作区配置，包括模型覆盖。原生 DSH 工作区 UI 本身区分 ready/loading，本插件丢弃了这些元数据。

建议：完整成功快照才能做删除对账；加载中、失败和断线保留配置；删除动作应有清晰的宿主确认语义。工作区列表变化与普通模型保存不应混成隐式批量删除。

### 4. P2，core：独立包的安装说明不能兑现原生子代理配置【静态确认】

位置：`core/SETUP.md:5`、`core/README.md`、`core/ROUTING.md`、`scripts/build-release.mjs`。

通用 ZIP 只打包 core，SETUP 明说不负责原生安装，却指向不在包内的 adapters/project 和已不存在的 plugins/ 目录；README 仍称 4.5.0 本地候选。核心路由让 Codex/Claude/独立工作流读模板，模板又要求 doctor，但纯 core 包不包含该平台适配器。照此入口不能完成原生角色发现和调用验收。

仓库根 SETUP 与 adapters/project 已支持 Codex/Claude 的原生安装；不能把这等同于下载的通用 ZIP 已包含这些能力。旧适配表对 Cursor/Pi/DSH/generic 也明确只有入口，不具备完整多代理适配。

建议：保留平台无关 core；为独立发行补齐可获取的安装适配入口和能力矩阵，输出已识别 harness、配置来源、可用工具、角色发现、调用实测结果。支持的宿主走原生工具，不支持时明确停止多代理验收。Node 指令模式不能被称为原生代理模式。安装成功与多代理验收成功分开。

### 5. P2，DSH：空工作区列表会复活已删除配置【组件夹具已复现】

位置：`dsh/client/index.mjs:945`、`:961`；`dsh/config.mjs` 的 pruneProjects 也保留空列表场景。

即使宿主返回成功的空列表，面板也回退到 state.projects，因此已删除工作区再次出现在选择菜单，不能满足自动检测删除的设计。列表不可用与确实没有工作区应分别表示。当前注入声明也未声明 workspaces/sessions，面板依赖可选 ctx.get 或上层 props；真实入口是否稳定提供这些服务需要宿主验收，不能由测试 double 推定。

### 6. P2，DSH：绿点代表局部开关而非实际启用【组件夹具已复现】

位置：`dsh/client/index.mjs:971`。

总开关关闭、工作区 enabled=true 时仍显示绿点，与用户要求的“在此工作区已启动工作流”不符。应统一使用有效状态，至少合并总开关与工作区开关，并明确草稿与已保存状态。

### 7. P2，DSH：设置入口的会话工作区解析不具备完整订阅【静态确认】

位置：`dsh/client/index.mjs:898`、`:914`，对照同文件 ConversationDashboard 对 sessions.list 的订阅。

设置 Card 用 useMemo 解析会话 cwd，仅依赖 ctx 对象、sessionId 和初始路径。会话数据异步到达且这些引用不变时，不会重新解析；切到无法解析工作区的新会话时又仅在 cwd 非空才更新选中路径，可能保留上一个会话的配置目标。右/下侧栏自动进入当前聊天工作区的要求尚未被充分保障。

建议：统一订阅会话与工作区原生 store；切换时立即清除旧目标，解析成功前禁用目标写入，不猜测其他工作区。

### 8. P2，DSH/Codex：原生调用与持久台账仍依赖主代理手动补记【DSH 夹具已复现】

位置：`dsh/index.mjs:175`、`:189`、DSH 技能第 5 条；Codex ROUTING 的派发后记录要求。

DSH startActivation 成功后，核心 activity 仍为空，原生终态只更新内存；这是现有“宿主不直接写项目”边界下的设计。主代理如果已保存 requested，却未同步结束状态，下一次派发会因旧非终态被阻止，即使本插件内存已观察到完成。若完全没有落盘，插件重载又会丢失防重复信息。

建议：通过符合宿主权限的原生记录桥完成启动与终态持久化、失败补偿和冷恢复对账。无法写台账时明确显示“已启动但未登记”，保留真实 ID，阻止盲目重派。不得为了自动登记改用插件宿主 fs 绕过项目权限。Codex 同样需要真实原生观察的登记/恢复流程，而不是虚构一个 MCP 启动器取代当前会话原生工具。

### 9. P2，三端共享：工作区与子项目运行归属、快照边界未拆开【静态确认】

位置：`core/scripts/loop.mjs:69`、`:115`、`:278`，DSH 技能项目根定义。

当前运行集中于传入 ROOT 的 `.ai-loop/runs/`。DSH 以会话工作区为 ROOT，记录存于“插件开发/.ai-loop”符合当前契约，不表示 scribe 随意写错目录；但运行没有独立的子项目分类定位机制。任务 in_scope 用于调度冲突，并不会限制 run 快照，快照默认遍历整个 ROOT；其他插件的变化会使当前子项目证据失效。

建议：分别声明 workspace_root、project_root/工作范围、run 存储位置与 snapshot_scope；默认工作区集中记录并提供子项目分类/筛选，独立项目模式显式选择。不要直接把 runs 改成任意嵌套目录，现有读取脚本、恢复与看板都依赖扁平 run_id，需要兼容迁移及明确共享依赖范围。

## 已有合理设计

- Codex 生成 `.codex/agents/loop-*.toml` 或用户级 `agents/loop-*.toml`，使用 name/description/developer_instructions/model 等原生字段；未用 shell 启动另一个 CLI 冒充当前会话子代理。当前会话实际也已发现五个 loop 角色，但“发现”不代表“本轮执行”。
- DSH `ai_loop_delegate` 确实调用原生 `startActivation(provider=spawn)`，检查独立上下文、模型覆盖与深度能力；具有模型预检、阶段/attempt 校验、启动中并发占位与在途重复检查。不能将整个 DSH 插件笼统称为假调用。
- 核心有快照匹配、修复预算、批次、DAG、互斥开发范围、测试/评审收敛与未知模型/usage 标记。子代理结束不直接等于任务 PASS，方向正确。
- Codex doctor 明确区分配置检查、原生发现、实际执行、模型与界面；disabled/blocked 不应冒充已启用。

规范依据：[OpenAI 原生子代理文档](https://learn.chatgpt.com/docs/agent-configuration/subagents)。该文档支持独立 TOML 自定义角色，并明确原生角色配置与实际委派工具的职责。DSH 接口还通过本机 DeepSeek Harness app.asar 中原生工作区组件只读核对：工作区数据含 path/workspaceId，宿主区分 phase/state；本轮未操作真实客户端界面或发起模型推理。

## 待确认的实施方案

本方案预计修改 3 个以上源码/测试/说明文件，按用户规则先等待确认，尚未编码。

1. **共享核心先补执行证据契约。** 修改 loop/activity 与角色报告协议，新增可区分真实原生派发和 self 的执行关联；覆盖任务评审、最终评审、过期批次、终态及旧版本兼容。旧运行保留原证据，不自动改成 verified。
2. **修复 DSH 派发规则与记录链。** 区分主/叶角色，统一 lite、角色开关、用户单代理与多代理必需模式；使用原生权限路径登记启动/结束与恢复对账，不改变宿主权限。
3. **修复 DSH 工作区面板。** 订阅原生会话和工作区完整状态；空列表与加载失败分别处理；保存不隐式删除未知配置；统一有效开关绿红点，覆盖右侧/下侧入口与异步会话切换。
4. **适配 core/Codex。** core 提供明确可用的 harness 安装/能力矩阵及验收入口；Codex 保留原生 loop 角色与工具，补派发证据/缺失时显式提示/恢复核验。不能将 DSH 的 ai_loop_delegate 或它的 UI 插槽照搬到 Codex。
5. **增加子项目归属和分类。** 保留现有 runs 兼容结构，增加运行级范围与筛选，明确快照与共享依赖；不移动现有用户记录，迁移另行预演。
6. **更新回归与交付。** 对上述复现增加有效回归，更新三端文档和开发交接，在正常用户宿主完成受保护写入测试，再重建核验三种包。真实宿主用只读小任务验收原生 ID、上下文、有效模型、结果与 UI；仅文件检查或 mock 通过不算原生验收通过。

预计涉及 core/scripts/{loop,activity,memory}.mjs、core/{WORKFLOW,MEMORY,SETUP,README,ROUTING}.md、角色/路由模板、adapters/project 安装诊断、codex 技能/路由/诊断/看板、dsh/index.mjs、dsh/client/index.mjs、相关测试及构建产物。具体增减围绕以上验收，不修改 settings.json，不默认安装或发布。
