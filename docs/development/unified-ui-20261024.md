# 工作区配置与双页工作流面板

## 目标与范围

本阶段根据已确认的 `proposal.md`，将 AI Loop 设置与子代理观察入口收拢为“工作流配置”和“工作流看板”两页；配置与运行查询以宿主的工作区为边界，窄面板使用由上至下的任务和调用树。源码基准是 `dev/codex` 的 `e152efc`。本说明记录实现结构和必须保留的能力边界；本机运行 `unified-ui-20261024` 的最终测试、构建及评审报告才是本次结果的依据。

Codex MCP App 从工作流工具打开同一面板，并声明 thread 与 global 两类官方入口。面板默认显示配置页，顶部选择工作区，另一页显示纵向看板。入口请求不提供当前聊天 ID；仅收到真实聊天标识时，服务端才可按 `thread-project-assignments` 精确映射工作区。没有可靠标识时显示“未定位”并允许手选。DSH 在侧栏使用相同页签和字段顺序，顶部工作区选择由两页共享；手选其他工作区后查询该工作区运行，回到聊天所属工作区才恢复聊天过滤。工作区删除会清空选择，重新出现时不自动选回。聊天页继续展示该聊天的纵向看板。

## 工作区身份与配置

Codex 的候选列表来自桌面状态中的 `local-projects`。字典键是工作区 ID，`rootPaths` 是其成员目录：多根工作区在选择器中只有一项，同名不同 ID 仍分开。新版状态存在时即使列表为空，也不拼入 active、saved 或插件历史目录；只有无法使用新版字段时才进入明确的 legacy 根目录模式。桌面状态只读。每次打开或刷新、面板重新取得焦点以及面板可见时，重新读取列表；过期选择会被清除。

插件的 `workspaces.json` schema 2 按工作区 ID 保存启用状态和集中配置。绿色、红色状态反映已保存状态，草稿另行标示；新工作区默认停用。DSH 使用宿主返回的规范工作区路径作本平台身份，重复路径合并，并从已保存配置计算状态点，不把当前草稿当作已启用。

旧 Codex 根级模型配置迁移到工作区时先检查所有成员根。配置一致或只有一个旧配置时可作为迁移来源；存在差异时页面展示成员根选择，必须明确选中来源才能保存。启用状态冲突也必须由用户在面板选定。草稿绑定全部成员的配置基线，包含原先没有配置的成员；选定来源后，其他成员的配置被修改或新建都会使基线失效并拒绝覆盖。多根模型保存会先对全部成员根预演，在事务锁内、每个成员写入前和登记提交前验证工作区 ID、成员列表和配置基线，再保存原生角色文件和工作区注册记录；任一成员失败时按写入前的文件字节恢复。不同工作区共享物理根会阻止写入，避免配置交叉影响。旧工作区记录和运行历史不会因宿主列表删除项目而被复活或自动搬迁。

面板草稿由独立 MCP manager 实例隔离，并按配置范围及工作区身份区分。切页和列表刷新保留草稿；工作区被删除后，后续保存重新检查宿主列表并拒绝旧目标。服务最多保留 64 个实例，达到上限时只回收所有范围均无草稿的实例；仍有草稿时保留，并在全部实例均有草稿时提示先保存或放弃。被回收实例不能直接提交动作或单字段更新；页面重建时明确恢复所选工作区和范围，避免把空实例当作保存成功。统一保存或放弃动作返回结果给原面板。启用状态只有保存完成后才刷新。

SessionStart 入口须把当前目录匹配到仍存在的宿主工作区成员根，并确认该工作区已启用后才加载工作区配置。真实 `session_id` 与其工作区上下文可用于看板筛选。它不会从选中的全局项目、插件工作目录或活跃根目录推断聊天归属。

## 面板与展示契约

Codex 的 `ai_loop.panel.read/update/action` 为每个面板实例提供读、暂存及保存/放弃/恢复继承能力；原生插件设置接口仍为兼容入口。`ai_loop.dashboard.runs` 和 `history` 可按 `workspace_id` 查询所有成员根，并把实际记录根附在运行条目上；看板单次状态查询仍针对记录所在成员根。历史请求按真实聊天隔离，游标绑定工作区和聊天。

两端沿用主代理、正式任务、代理调用的由上到下单列结构；调用详情折叠显示，真实可导航 ID 才提供打开会话按钮。Unknown token usage 显示不可获取，不以零冒充。两端复用 `core/scripts/ui-theme.mjs` 中的颜色语义、间距、字号、圆角和层级缩进，再由 Codex 原生 Canvas 主题与 DSH CSS variables 适配。Codex 保留无外部网络依赖的内嵌 MCP App；DSH 保留其 React client 和原生侧栏接口。刷新不重新选择工作区，只有面板首次取得入口上下文或上下文标识变化才重新定位聊天。

## 宿主边界与验收

Codex 官方入口契约允许插件声明 thread 和 global 入口；目前方案没有证明插件能强制把图标固定放在右侧工具栏。当前会话若无可验证映射，面板允许手选工作区。交互夹具用于检查页面结构和窄宽度布局，不等于 Codex/DSH 实际插件页验收。MCP `ui/open-link` 的协议请求也不等于宿主已成功打开子代理会话。

本次续接中，浏览器和 Windows 界面运行时均在初始化时报告 `invalid local executable configuration`。这是本机自动化组件启动失败，未取得本轮真实界面截图；不能将单元测试、可点击夹具或已打开的预览页作为宿主视觉验收结论。

在源码树执行 `node tests/all.mjs`、`node scripts/build-plugin.mjs --check`、`node scripts/build-dsh.mjs --check` 和 `node scripts/build-release.mjs`；检查工作区增删、同名不同 ID、多成员身份、聊天归属、旧配置冲突及用户选源、事务回滚、刷新/草稿隔离、状态点和窄视图。Codex Windows owner 预检是写配置的现有保护，测试必须使用隔离夹具并尊重该检查，不通过修改 ACL 或所有者来让写入夹具通过。最终退出码、日志和独立评审状态以本次运行目录中的原始报告为准。真实客户端中的入口位置、面板主题、会话导航和实际工作区列表仍需宿主单独验收。

## 本阶段验证记录

2026-10-24，真实原生 `loop-tester` 在 Windows 正常用户宿主中执行隔离测试；评审前快照的 `node tests/all.mjs` 共 245 项，239 项通过、0 项失败，6 项因 Windows 创建符号链接返回 `EPERM` 而跳过。Codex 53 个文件和 DSH 32 个文件的构建一致性检查、`git diff --check` 均通过。首轮发现的旧启动钩子夹具只登记根路径、缺少宿主工作区记录，已补齐 `local-projects`，并保留“旧登记不能代替当前宿主工作区”的断言。独立评审随后发现旧根迁移的全成员并发基线缺口和面板实例累计耗尽问题；修复后新增回归，最终测试与复审结果以本次运行的最新报告为准。

第二轮修复后的完整验证为 250 项，244 项通过、0 项失败，6 项仍因 Windows 创建符号链接返回 `EPERM` 而跳过。新增回归覆盖未选迁移成员被外部修改、无配置成员被外部新建配置、超过 64 次打开干净面板、全部实例有草稿时拒绝驱逐以及失效实例拒绝提交。`node scripts/build-release.mjs` 成功生成通用、Codex、DSH 三种本地产物；`node scripts/build-plugin.mjs --check`、`node scripts/build-dsh.mjs --check` 和 `git diff --check` 均通过。构建检查命令已按真实执行记录核对，未执行的参数形式不能作为证据。新增共享交接后的最终快照仍须通过核心验证与独立评审门禁。

此次补修覆盖 ID 注册表的并发变更检测、全局草稿跨工作区保留基线、注册表提交失败时模型文件的字节回滚，以及 DSH 两页共用工作区和查询范围。三版本产物已在本地生成，未安装、未发布。真实独立评审及最新完整快照结论以运行 `unified-ui-20261024` 的最终报告为准；实际模型、宿主入口位置、主题和会话跳转仍须实机验收。本轮界面自动化因运行时启动配置无效而未能进行视觉验收。

第三轮评审指出两处成员配置基线问题：全局继承工作区缺少成员实际配置摘要，阻断后续保存专属覆盖；首次迁移仅选择来源时，刷新可能替换成员基线并允许覆盖外部更新。修复为继承读取返回逐成员摘要（含无配置成员），继承记录上的全局摘要不再作为成员旧配置依据；选源草稿在首次选择时捕获所选源摘要，后续 `read` 保留原始全成员基线。回归通过真实 manager 生命周期覆盖单根/多根、全局配置存在/缺失下恢复继承后保存模型、并发和思考深度；仅选来源并刷新后拒绝外部成员配置变化（检查成员字节与注册记录未部分写入）；无外部变化时仅选来源仍可完成迁移。修复前和修复后定向日志保存在运行 `reports/`；测试运行身份与命令退出码以新增原始日志及 tester 报告为准。

R5 专项运行 `unified-ui-r5-20261024` 接续已停止的 `unified-ui-20261024`：旧运行保持 stopped、fixes=3，所有旧报告和快照不改写；新运行以第三轮修复快照 `f141b9286457265cb58c56b27d25b11786b4488a5ac81e6dead70b1fc37b7b19` 为基线，单独记录 R5。R5 根因为只有 id/roots/enabled 的工作区状态登记被误判为迁移完成，导致选择旧模型来源后 `apply` 清除草稿却未保存集中 profile。修复迁移完成条件为存在有效集中 profile；明确全局继承分支仍直接返回，不重复迁移。真实 manager 红灯先复现缺失集中 profile；补修后相关原生设置与工作区测试 63 项通过，日志位于新运行 `reports/r5-red-assertion.log` 和 `reports/r5-green.log`，执行身份均为提升命令中的 Rainwood。外部更新（包括原空成员后来出现配置）拒绝保存且保留配置字节；仅状态登记后保持启用状态并物化所有成员，已有集中 profile 与明确全局继承不重复物化。此记录不代表全量验证或独立评审通过；这些仍由 R5 新运行后续阶段完成。Codex/DSH 实际入口、主题、模型和会话导航仍需宿主实机验收。
