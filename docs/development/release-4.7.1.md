# 4.7.1 旧记录兼容修复与两端安装

日期：2026-10-27。基线：`52017dd`（4.7.0）。用户已确认修复旧记录兼容缺陷、补回归、发布 4.7.1 并安装到 Codex 与 DSH desktop。保留模型、思考深度、角色状态、并发、工作区和历史运行；不修改 settings.json、权限或钩子信任。

## 实际触发与根因

4.7.0 的两端原生安装和文件摘要验证通过，Codex MCP 也实际返回 4.7.0，初始化和只读工具可用。但已安装版本 doctor 在读取实际旧运行 `codex-live-audit-20261026` 时，抛出“流程边 audit → audit 与 depends_on 反向”。原记录的 tester → reviewer 是同一正式任务内的合法阶段交接。`analyzeWorkflow` 把这种边拿去检查任务之间的依赖，而可达函数把任务自身判为可达，形成误报。上一轮全量及独立评审漏掉了持久化同任务阶段图这一场景。

修复该错误后，实际工作区恢复又暴露出“运行不存在：three-version-repair-20261023”。新版发现逻辑扫描相邻子目录，把原来以子目录为独立根创建的本地运行也纳入父工作区，但该记录的 project_path 是根目录 `.`，不属于父工作区的子项目记录。原项目根直接读取始终是合法入口。

## 修复范围

- 同一任务内部的流程边跳过跨任务 depends_on 语义检查，图节点的真实循环检测照常执行。
- 跨任务反向依赖仍拒绝；流程边没有声明依赖时仍只展示警告，不增设执行授权。
- 父工作区仅纳入能归属到该工作区的记录。相邻独立子工作区的根运行不参与父工作区查询或运行编号解析，在其原根继续访问。
- 不改写旧 spec/state/events/checkpoint，不重置阶段、计数或既有证据，不自动迁移记录位置。

## 回归与发布门禁

新增用例先在 4.7.0 实现复现失败，再验证修复：同任务 dev → tester → reviewer、真实图循环、跨任务正常/反向依赖、4.6.4 持久化旧记录恢复及字节保留、独立子工作区归属和原根恢复。

同时只读重放实际工作区的旧活跃记录，并监控旧 spec/state/events/checkpoint/session 摘要。完整套件使用 `node tests/all.mjs`；发行使用 `node scripts/build-release.mjs`，两包 `--check`、SHA256SUMS 及旧包保留分别核验。

修复前已安装版 doctor 无法完成，因此先由主代理修复和执行验证；不绕过 doctor 派发门禁。新候选通过完整回归后由原生安装器更新，doctor 与受管理角色路径通过后再进行独立验证和评审，正式发布保留该证据门禁。最终结果和资产摘要见 [v4.7.1 Release](https://github.com/murenyu1/ai-loop-engineering/releases/tag/v4.7.1) 与本机运行 `hotfix-4.7.1-20261027` 的 reports。

## 安装与边界

Codex 通过原生 marketplace/plugin 命令安装；全局及当前工作区受管理角色只更新插件引用，保留各自 profile。DSH 通过原生管理器离线更新 desktop，禁用安装脚本，不更改 cordis 模型配置。安装前备份、安装后按完整文件清单核对摘要，并检查 settings.json 和工作区登记未变。

安装文件及独立 MCP/配置检查不代表当前已打开的页面或代理已经热更新。客户端重载后的实际页面、钩子和底层模型执行需分别验收；不自动关闭正在使用的两端桌面程序。Windows 符号链接权限跳过项如实记录，不声明通过。
